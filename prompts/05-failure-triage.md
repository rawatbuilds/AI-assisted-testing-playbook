# Prompt 05: Failure triage

**Goal:** cut the time from "CI is red" to "I know which kind of problem this is".

The prompt itself is generated by `scripts/triage_failures.py`, which first clusters failures by error signature (30 failures are often 3 causes) and **redacts** emails, tokens, cookies, long hex ids and card-like numbers.

## Prompt template (what the script emits)

```
You are helping a QA engineer triage failed automated tests. ...

For EACH cluster:
1. Give up to 3 ranked root-cause hypotheses (product bug, test bug, environment, test data, timing).
2. For each hypothesis, name the specific evidence that would confirm or rule it out
   (trace step, network call, console log, recent commit, data state).
3. State what you CANNOT determine from this text alone.

Rules: do not propose code fixes yet; do not claim certainty; say "unknown" where the
information is missing; do not invent selectors, endpoints or log lines.
```

## How I use the output

1. AI output is a list of **hypotheses**, not a diagnosis.
2. I open the Playwright trace and verify the top hypothesis against evidence (network call, DOM state, timing).
3. Only then do I fix, and I re-run the failing test several times to confirm it is stable (`--repeat-each=10`).

## Why clustering first

- Sending one failure per prompt wastes time and context.
- A `network` cluster (DNS failure, connection refused) means the environment is broken, not the product. No AI needed.
- It keeps the prompt small, so there is less data to redact and less risk of leakage.

## Known failure modes

- Confidently blames the product when the real cause is test data or timing.
- Suggests adding `waitForTimeout`, which hides flakiness instead of fixing it.
- Invents a plausible-sounding log line that was never in the input.
